🤖 Módulo 02

¿Qué es el Testing
Automatizado?

El testing automatizado es el proceso de usar herramientas y scripts para ejecutar pruebas de software de forma automática, sin intervención humana directa durante la ejecución.

📌 Definición formal

Es el uso de software especializado para controlar la ejecución de pruebas, comparar resultados reales con resultados esperados, y reportar el estado de las pruebas, todo de manera sistemática y repetible.

Ejemplo concreto

Imagina que tienes un formulario de login. Manualmente un tester lo prueba 1 vez. Con automatización, ese mismo test se ejecuta con 50 combinaciones de datos, en 5 navegadores, en cada commit del desarrollador.

// Test automatizado de login (Cypress) describe('Login Form', () => { it('should login with valid credentials', () => { cy.visit('/login') cy.get('#email').type('user@test.com') cy.get('#password').type('secret123') cy.get('[data-cy=submit]').click() cy.url().should('include', '/dashboard') }) })
Lo que no es
❌
No es magia
Alguien debe diseñar, escribir y mantener los tests. No se automatiza solo.
❌
No reemplaza el juicio humano
Los scripts validan lo que se les programó. No detectan problemas inesperados de UX.
❌
No es gratis
Requiere inversión inicial en tiempo, herramientas y conocimiento técnico.
🎯 Módulo 03

Objetivos del Testing
Automatizado

La automatización no es un fin en sí mismo. Tiene objetivos claros que justifican la inversión y el esfuerzo técnico.

⚡
Eficiencia

Ejecutar cientos de pruebas en minutos, no días. Liberar al equipo de trabajo repetitivo para enfocarse en análisis crítico.

🛡️
Calidad Continua

Detectar regresiones apenas se introduce un bug. El sistema siempre está siendo validado, no solo antes del release.

🌐
Cobertura Amplia

Probar miles de combinaciones, múltiples navegadores, sistemas operativos y dispositivos simultáneamente.

🎯
Precisión

Eliminar errores humanos por cansancio o distracción. Una máquina ejecuta el mismo test de la misma forma siempre.

🔁
Repetibilidad

El mismo test puede ejecutarse infinitas veces sin degradación. Ideal para regresiones y validaciones frecuentes.

💰
Reducción de Costos

A largo plazo, el costo por ejecución de test cae drásticamente. ROI positivo después de la inversión inicial.

✅ Módulo 05

¿Qué se debe
Automatizar?

No todo merece ser automatizado. Los mejores candidatos son aquellos tests que se repiten frecuentemente, son críticos para el negocio y representan áreas estables del sistema.

Candidatos ideales
🔁
Pruebas de regresión
Todo lo que se prueba en cada release: login, checkout, búsqueda, pagos. Se ejecutan cientos de veces.
🔌
Testing de APIs
Validación de endpoints: status codes, payloads, tiempos de respuesta, autenticación. Alta ROI.
📊
Validaciones de datos
Campos obligatorios, formatos, rangos válidos. Tests repetitivos que un humano hace igual cada vez.
⚡
Tests de performance
Carga, stress, volumen. Simular miles de usuarios simultáneos. Imposible hacer manual.
🌐
Cross-browser/device
Ejecutar el mismo flujo en múltiples navegadores y resoluciones en paralelo.
Criterios de selección
Frecuencia de ejecuciónAlta = automatizar
Criticidad para el negocioAlta = automatizar
Estabilidad del flujoAlta = automatizar
Volumen de datos/casosAlto = automatizar

"Automatiza lo que se repite. Preserva el juicio humano para lo que requiere creatividad."

❌ Módulo 06

¿Qué NO debería
Automatizarse?

Automatizar sin criterio es uno de los errores más costosos en QA. No todo test representa un buen candidato para automatización.

🔍
Pruebas Exploratorias

El testing exploratorio requiere creatividad, intuición y adaptación en tiempo real. Un script no puede "improvisar" para descubrir bugs inesperados.

Requiere criterio humano
🎨
UX y Usabilidad Compleja

¿El botón está en el lugar correcto? ¿El flujo se siente natural? ¿Los colores generan confianza? Esto lo evalúa un humano, no un script.

Percepción subjetiva
🚧
Funcionalidades Temporales

Una feature que cambiará en 2 semanas no vale la pena automatizar. El costo de mantener el script supera el beneficio.

ROI negativo
🌊
Sistemas Inestables

Si el sistema cambia constantemente, los tests automatizados se romperán en cada sprint. El equipo pierde tiempo manteniendo scripts en vez de crear valor.

Alta tasa de fallos
Análisis Costo vs Beneficio

Antes de automatizar, pregúntate:

📅

se ejecuta?

🔧
¿Cuánto cuesta
mantenerlo?
Tests frágiles cuestan más que ejecutar manual
💡
¿Qué se gana
realmente?
Velocidad, cobertura, confianza — cuantifícalo

"Automatizar mal es peor que no automatizar. Un suite de tests frágiles genera desconfianza y desperdicia tiempo del equipo."

Unit Tests

Prueban la unidad mínima de código: una función, un método, una clase. Son rápidos, baratos y forman la base de cualquier suite sólida.

Validan que múltiples componentes funcionen correctamente juntos: servicios, bases de datos, APIs internas. Detectan problemas de contrato entre módulos.

API Testing

Valida los endpoints de la aplicación: status codes correctos, estructura del payload, tiempos de respuesta, autenticación y autorización.

Son más estables que los tests de UI porque no dependen del HTML/CSS de la interfaz. Cambia la UI, el API sigue igual.

UI / E2E Tests

Simulan las acciones de un usuario real: clicks, escritura, navegación. Prueban el sistema completo de principio a fin.

LentosFrágilesAlta confianza

Son los más costosos de mantener pero los más cercanos a la experiencia real del usuario. Úsalos para flujos críticos.

3. Ingresar credenciales
4. Click en "Entrar"
5. Verificar dashboard

Garantiza que el nuevo código no rompe funcionalidades existentes. Es el caso de uso más común y justificado de la automatización.

CI/CD y Testing
Automatizado

La integración continua y la entrega continua son el entorno natural del testing automatizado. Sin CI/CD, el testing automatizado pierde gran parte de su valor.

¿Qué es CI/CD?
🔄
CI — Continuous Integration
Cada cambio en el código se integra automáticamente. Se ejecutan tests para detectar errores al instante.
🚀
CD — Continuous Delivery
Si los tests pasan, el código puede desplegarse automáticamente a producción o un entorno de staging.
🛡️
Tests como puerta de calidad
Un pipeline sin tests que pasen no puede avanzar. Los tests son el guardián automático de la calidad.

⚠️ Módulo 12

Limitaciones del Testing
Automatizado

Una visión honesta y equilibrada de las limitaciones es esencial para implementar automation de forma estratégica y no caer en trampas costosas.

💸
Costo inicial alto

Requiere tiempo de ingeniería especializada, licencias de herramientas, y configuración de infraestructura antes de producir valor.

Inversión antes de retorno positivo

🔧
Mantenimiento constante

El sistema evoluciona y los tests deben evolucionar con él. Un test que no se mantiene se convierte en deuda técnica.

10-30% del tiempo se dedica a maintenance

🧠
Requiere habilidades técnicas

No cualquier tester puede escribir scripts. Requiere programación, entender CI/CD, manejo de frameworks y pensamiento analítico.

Brecha de habilidades en el mercado

⚠️
Falsos positivos/negativos

Tests mal escritos fallan cuando no deben (flaky tests) o pasan cuando deberían fallar. Generan desconfianza en el equipo.

"Flaky tests" son el gran problema del sector

🏆 Módulo 13

Buenas Prácticas
en Automation

La diferencia entre un suite de tests que agrega valor y uno que genera frustración está en seguir principios sólidos desde el principio.

🎯
Prioriza pruebas críticas
Automatiza primero lo que más duele: login, checkout, pagos, flujos de negocio críticos.
🧩
Reutiliza código (Page Objects)
Encapsula la lógica de la UI en objetos reutilizables. Si cambia el selector, cambias en un solo lugar.
⚡
Mantén tests independientes
Cada test debe poder ejecutarse solo, sin depender del estado de otro test.
📊
Nombres descriptivos
El nombre del test debe decir qué prueba y qué espera. "should_show_error_when_password_is_short"
🔗
Integra con CI/CD
Los tests sin pipeline son tests que nadie ejecuta regularmente. Automatiza la ejecución.
📝
Reportes claros
El equipo debe poder entender qué falló y por qué en segundos, sin leer código.
❌
No automatices todo desde el inicio
Empieza con lo más crítico. Automatizar todo sin criterio genera suites frágiles e inmantenibles.
❌
No uses sleeps fijos
wait(3000) hace los tests lentos y frágiles. Usa esperas condicionales inteligentes.
❌
No ignores los tests que fallan
Saltear un test roto es ocultar un problema. El equipo pierde confianza en la suite completa.
❌
No uséis selectores frágiles
Seleccionar por XPath complejo o posición CSS es una bomba de tiempo. Usa data-testid atributos.
❌
No dependas del orden
Si el test B depende de que el test A se ejecutó antes, tienes un problema de diseño.
❌
No probar implementación
Prueba comportamiento, no código interno. Los tests no deben romper cuando haces refactoring válido.
🏗️
Page Object Model

Patrón de diseño que encapsula la UI en clases. Cuando el diseño cambia, solo actualizas el Page Object, no todos los tests.

🎭
AAA Pattern

Arrange — configurar el escenario. Act — ejecutar la acción. Assert — verificar el resultado.

🔢
Data-Driven Testing

Un solo test, múltiples conjuntos de datos. Prueba el login con 20 combinaciones usando el mismo script.

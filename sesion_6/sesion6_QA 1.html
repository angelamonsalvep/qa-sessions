Tema 1 — Diseñar vs. ejecutar
El punto de partida
No es lo mismo diseñar que ejecutar una prueba
❮ Ejecutar
Acción humana

Abro el navegador, escribo el usuario, hago clic, veo qué pasa. Es variable. Cada vez puede ser distinto. No es reproducible con exactitud.

❯ Diseñar
Plano previo

Antes de tocar código: defino exactamente qué datos entran, qué acciones ocurren en qué orden, y qué debe ser verdad al final. Determinista. Reproducible por una máquina.

"Si dos QA engineers diseñan la misma prueba de login sin ponerse de acuerdo, ¿cubrirían exactamente lo mismo?"
Analogía del puente
→
Un obrero construye el puente. Pero antes alguien lo diseña: planos, medidas, cargas.
→
Sin diseño, cada obrero construye algo diferente. Con las pruebas pasa exactamente lo mismo.
→
El código de automatización es la transcripción del diseño, no el diseño en sí.
⚠ El diseño ocurre antes del código. Siempre.

Tema 2 — Flujo de usuario
Modelado del flujo
Todo flujo de usuario tiene 4 componentes
01 · INICIO
Punto de entrada
¿En qué estado está el sistema antes de que empiece la prueba? El usuario llega a la página de login sin estar autenticado.
›
02 · ACCIONES
Lo que hace el usuario
Escribe email → escribe contraseña → hace clic en "Ingresar". Orden exacto, sin ambigüedad.
›
03 · DECISIONES
Bifurcaciones del sistema
¿Son correctas las credenciales? Cada decisión genera al menos dos flujos distintos.
›
04 · RESULTADO
Estado esperado final
Si credenciales válidas → dashboard. Si inválidas → mensaje de error específico visible.
Ejemplo — Login
✓
Inicio: usuario en /login sin sesión activa
✓
Acciones: ingresar email → ingresar pass → clic en "Ingresar"
✓
Decisión: ¿credenciales válidas?
✓
Resultado exitoso: redirige a /dashboard
⚠ Error común
Los estudiantes modelan solo el camino feliz. Un flujo sin bifurcaciones no está completo. El login tiene al menos 4 flujos: exitoso, contraseña incorrecta, usuario no existe, campo vacío.

Tema 4 — Assertions
El corazón de la prueba
Una assertion es una afirmación verificable
Definición

"En este punto de la prueba, esto DEBE ser verdad. Si es verdad → prueba pasa. Si no es verdad → prueba falla."

"Una prueba sin assertions no prueba nada. Es un script que solo ejecuta acciones — como un tester que no mira si el resultado es correcto."
Analogía del árbitro
→
El árbitro no juega — observa y verifica.
→
La assertion es el silbato: lo usas cuando algo debería haber ocurrido y quieres confirmarlo.
→
Si el balón cruzó la línea → assertion: "El marcador debe mostrar 1".
Tipos de assertions (sin código)
?
¿Está este elemento presente en pantalla?
?
¿Contiene este texto específico?
?
¿La URL es la correcta?
?
¿El elemento está habilitado o deshabilitado?
?
¿Cuántos elementos de este tipo hay?
?
¿El total es igual a la suma de los ítems?
⚠ Pregunta trampa: si hago login exitoso pero no agrego ninguna assertion, ¿puede la prueba reportar que pasó aunque haya un bug?

Tema 5 — End-to-End Testing
Visión completa del usuario
Una prueba E2E simula el recorrido completo de un usuario real
¿Qué valida?

No una función aislada — todo el sistema tal como el usuario lo experimenta. Buscar → agregar al carrito → pagar → recibir confirmación. Eso es E2E.

¿Cuándo usarlo?

Cuando el valor del negocio depende de que varios sistemas trabajen juntos. Login, checkout, onboarding, flujos críticos de negocio.

⚠ E2E ≠ automatización total. Es un tipo dentro de la pirámide de testing. No reemplaza los tests unitarios ni los de integración.
Ventajas
✓
Detectan bugs de integración que las pruebas unitarias no ven
✓
Validan la experiencia real del usuario, de punta a punta
✓
Dan confianza al equipo antes de un release
Limitaciones
✗
Son lentas: pueden tardar minutos por prueba
✗
Son frágiles: un cambio en la UI puede romperlas
✗
Son costosas de mantener: datos de prueba en múltiples sistemas
✗
Cuando fallan, el diagnóstico es difícil: ¿dónde está el bug?

›
ETAPA 03
Checkout

Errores comunes
Aprende de los errores más frecuentes
Los 6 errores que comete todo QA junior
Error 1
Confundir diseño con código

Creer que "diseñar la prueba" = escribir el script. El diseño ocurre antes, en lenguaje natural. El código es la transcripción.

Error 2
Solo el happy path

Modelar únicamente el flujo exitoso. Cada decisión genera al menos dos flujos. Un mapa sin bifurcaciones está incompleto.

Error 3
Assertions vagas

"Verificar que funciona", "que la página se ve bien". Debe ser verificable en binario: verdadero o falso. Sin ambigüedad.

Error 4
Inputs ambiguos

"Datos válidos", "email correcto". La máquina necesita user@test.com no "un email válido".

Error 5
E2E para todo

Querer automatizar como E2E algo que se cubriría mejor con un test unitario. Mayor costo, menor velocidad de feedback.

Error 6
Assertions frágiles de copy

Assertion sobre el texto exacto de un botón. Si el equipo cambia "Submit" por "Enviar", la prueba falla aunque no haya ningún bug.
